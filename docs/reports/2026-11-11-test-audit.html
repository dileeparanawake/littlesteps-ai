Every test passes: unit 214/214 (5.8 s, on a throwaway local database), browser 2/2 local (real OpenAI call) and 4/4 live signed-out. But no CI job runs any of them: a push to main deploys to Fly with no test step.

Top 5 risky tests

  1. The API route tests fake the access rules (about 20 tests).chat/route and threads/route replace enforceAccess with a stand-in that returns 401 or 403, then check the route returns it. The real rule list (/api/chat and /api/threads need sign-in) is never tested. Setting /api/chat to public would pass all 214 unit tests.one table test that calls each real handler (GET, POST, PATCH, DELETE) signed out and expects 401, with the real rules.
  2. "Someone else's chat" is only ever faked.userOwnsThread has no database test. The 403 tests give it a fake "no". A bug there would let one parent read, post to, rename or delete another parent's chat.a database test with two users: B gets 403 on A's chat for read, post, rename and delete.
  3. Token saving pins how many arguments a function gets (5 tests).They check addMessageToThread was called with exactly 3 or 4 arguments (call.length). Moving to an options object breaks them, with no change for users.send a message, then check the reply's row has its tokens and the weekly total went up.
  4. The usage-cap route tests are circular (7 tests).A stand-in returns 429 and the test checks the route returns 429. Two tests are the same. "Admin regardless of usage" never involves an admin. enforceUsageLimit is tested by spying on usageLimitInternal, an export that exists only for the tests.seed a week of usage at the cap, POST a question, expect 429 and no OpenAI call; an admin with the same usage gets 200.
  5. The browser test needs the live model to answer with a bullet list.chat-flow asks OpenAI for "3 tips as a bulleted list" and fails if the reply has no list. A model change or an odd reply makes it red, and each run costs a little.for the everyday run, check a reply appears and renders; keep one real-model run as a release smoke test.

1. The tests, by area

BEHAVIOUR checks what a parent, an admin or the cleanup job sees. DETAIL checks how it's built: which internal function was called, with which arguments, or a TypeScript type. BRITTLE checks a real behaviour but pins wording or a model's output.

Chat API route24 · 6 B · 17 D · 1 brittle

  • DETAIL 401 and 403 for POST and GET (4) The stand-in access check decides the status; the test reads it back.
  • DETAIL "calls enforceAccess with /api/chat" (2), "does not parse the body when denied" Call order and arguments, not an outcome.
  • DETAIL content extraction (2) and token usage (3) Read mock.calls by index and count arguments.
  • DETAIL usage cap: at cap, above cap (same test twice), below cap, admin Circular: a stand-in returns the answer.
  • BRITTLE "throws when WEEKLY_CAP_TOKENS is missing" Pins that the 500 reply shows the server's own error text. That also tells any visitor a setting's name: the route returns error.message as is.
  • BEHAVIOUR not your chat gives 403; existing chat keeps its id; new chat gets one; no OpenAI call and no reply saved when over the cap (6)

3. What to do, ranked

  1. Run the tests before deploy.Add a test job to the Fly workflow (unit tests with a Postgres service), and make deploy wait for it.~30 min. Without it, the rest only helps when someone remembers to run them.
  2. Replace the faked route tests with real ones.One table of route, method and "signed out / not yours / yours" against the real handlers, real rules and a local database. Then delete the 29 stand-in tests.~2 h. Covers risks 1, 2 and 4.
  3. Test what parents see for the limit, rename, delete and sign-out.Extend the one browser test, or add three short ones.~2 h.
  4. Stop sending server errors to the browser.The chat route returns error.message on a 500. Send a plain "Something went wrong" and log the detail. Update the one test that pins it.~15 min.
  5. Delete the tests that can't fail.main.test, the 4 type tests, "dates in UTC", the duplicate cap test.~10 min.
